# Over-execution regression — scope limit for the visualize skill (2026-11-07)

## 1. What happened

One daily request —

> 生成一个带 a、b、c 滑块的二次函数交互演示。

— produced **1 turn, 60 steps, 62 tool calls in 16.7 min** (session
`session-6ebab31e-6d40-4ca7-b2ad-6ef2b48cf143`, decompressed at
`tmp/session-overexec.jsonl`):

| Tool | Calls |
| --- | --- |
| `pwsh` | 39 |
| `visualize` | 11 (≈9 of them in-place patches; the skill itself says "at most 4 patches per reply") |
| `write` | 4 |
| `edit` | 3 |
| `skill` | 1 |
| `read` | 3 |
| `read_image` | 1 |

The card **rendered successfully on the third tool call** (seq 104: *"Rendered
… inline (18068 bytes via the sandboxed HTML fragment backend…)"*), yet the model
kept going: it wrote `window-check.mjs` and a 17 KB `card-check.cjs` DOM stub into
`%TEMP%\dsh-51kxcw\`, swept windows before it ever called `visualize` (*"I
verified the auto-window math first"*, seq ~120), reported **26,901 window
validations** (*"target(): checked 26901 windows, failures: 0"*) and **6,051 render
checks**, read the installed plugin's `lib/client.js`, and was still patching when
the turn ended. Nine assistant messages carried user-facing text, all English
process narration; the turn produced one card the user could have had in under a
minute. Workspace source was not modified (harnesses lived in `%TEMP%`), but the
model read plugin internals and burned the session.

## 2. Root-cause classification

1. **Model autonomy — primary.** The render succeeded; the model chose exhaustive
   verification and self-directed improvement anyway, and ignored the existing
   4-patch limit.
2. **Skill/examples — contributing.** Stage 7D had added wording that reads like a
   test suite: *"Axis direction letters are mandatory and are **graded**"*;
   *"Before returning, check: window fits… tick numbers do not collide…"*;
   `charts.md` full of numeric thresholds (≤9/≤7 labels, 22-28 % vertex band,
   ≥8 % margin, 1.4× span) with "measure/check" verbs; a 330-line example that
   looks like a spec. There was **no statement** that these are composition rules
   satisfied in one pass, and **no prohibition** on scratch files, harnesses,
   Node/DOM automation, or workspace writes, and no "the render ends the task".
3. **DSH host — enabling, not causative.** The daily GUI runs a coding agent with
   `pwsh`/`write`/`edit`, cwd = this repo, full access; it began with
   `git status`. The host permitted but never requested the harnesses; the plugin
   cannot change the host.
4. **Plugin renderer — no defect.** The `visualize` tool/lint/render behaved
   correctly (11 renders succeeded, patches applied). The plugin-side cause is
   skill wording only.

## 3. Wording changes (assets only, no src/tests/renderer)

- **`assets/visualize-skill.md`** — new **`## Scope`** block directly after the
  intro: a chat visualization request is one-shot authoring, not software
  development; read only the one or two references the card needs; call
  `visualize` once (a single patch only if the tool replies with an error); do
  **not** create or modify
  workspace files, scratch scripts, harnesses, fixtures or test data, do **not**
  run Node/DOM stubs/headless browsers/window sweeps/render loops; the tool's
  lint/render reply is the only runtime check and a rendered card ends the task;
  correctness is checked while composing, not by exhaustive sweeps; full test
  suites belong to plugin development; reply in the user's language in one or two
  sentences with no English engineering log and no interim progress messages.
- **`assets/visualize-skill.md`** — `"Axis direction letters are mandatory and are
  graded."` → `"Axis direction letters are required."`; `"Before returning,
  check: …"` → a **static** compose-time glance (*"read your own SVG once … not a
  test to run"*). All accuracy content kept.
- **`assets/references/charts.md`** — §Math function plots intro gains: the rules
  are **composition rules, not a test suite**; apply them while writing the
  fragment in one pass; no scripts/harnesses/Node/DOM stubs to measure or
  simulate; the tool's lint/render reply is the only runtime check and a rendered
  card ends the task.
- **`assets/examples/quadratic-explorer.html`** — header states it is a
  **composition reference**, not a module or test target: adapt it into the
  fragment and call the tool once; do not port its window function into Node or
  build a DOM stub around it.

> Note: the fixed-scope block is longer than the brief's 15-20-line estimate
> (~30 added lines) because each explicit prohibition (files, Node, DOM stubs,
> browsers, workspace writes, plugin internals, interim narration) is a separate
> failure mode observed in the incident.

## 5. Residual risk

1. **Time budget is not enforced by wording.** Tool discipline held in all six
   trials (≤6 calls, zero writes), but wall-clock varied 1m23s-6m40s with the
   same skill text. Nothing in the plugin can cap a turn.
2. **Reference reads vary** (2-4 files across trials). The Scope block now says
   "the one or two references the card needs"; steps stay within the 6-call
   budget regardless.
3. **Model autonomy remains the primary factor.** A future model can still choose
   to over-verify; the wording gives it strong, explicit permission to stop and a
   checklist it cannot mistake for a test suite.
4. The daily app/profile were not touched; trials ran only on the isolated
   profile. No `src/`, test or renderer changes; the fix is assets-only and
   reversible.
